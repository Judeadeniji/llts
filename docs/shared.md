# Shared Subsystems & Utilities

This document outlines the shared utilities and foundational subsystems in the `llts-zig` compiler. These encompass components found in `src/shared`, `src/io`, and `src/errors`, providing common types, diagnostics, and I/O operations used across the compiler pipeline (e.g., in the scanner, parser, and VM).

## Architecture & Data Flow

The `shared` module operates on primitive Zig arrays and string slices (`[]const u8`), avoiding any dynamic memory allocation. This zero-allocation design is intentional to keep common operator checks and precedence lookups as fast and lightweight as possible for the parser and compiler phases.

## Common Types & Data Structures

The utilities define static configurations for operators, grouped into structs that provide compile-time constants for matching strings.

### Operator Definitions (`ops.zig`)

Operators are represented as struct namespaces containing `values`, which is a static array of string slices.

```zig
// Binary Operators
pub const BinOps = struct {
    pub const values = [_][]const u8{
        "+",  "-",  "*",  "/",  "%",  "^",  "==", "!=", ">", ">=", "<", "<=",
        "&&", "||", "**", "|>", "..", "=>",
    };
};

// Unary Operators
pub const UnaryOps = struct {
    pub const values = [_][]const u8{ "!", "-" };
};

// Assignment Operators
pub const AssignOps = struct {
    pub const values = [_][]const u8{
        "=", "+=", "-=", "*=", "/=", "%=", "^=", "&&=", "||=",
    };
};
```

**Constraints & Rules:**
- Operator representations must perfectly match the token strings extracted during the scanning phase.
- `ops.zig` exposes API functions to validate if a specific string slice falls into one of the operator categories. These use linear search over the constant arrays:
  - `pub fn isBinOp(s: []const u8) bool`
  - `pub fn isUnaryOp(s: []const u8) bool`
  - `pub fn isAssignOp(s: []const u8) bool`

### Precedence Handling (`precedence.zig`)

Precedence rules for operations are centralized in the `PRECEDENCE` struct to guide the parser during expression evaluation.

```zig
pub const PRECEDENCE = struct {
    pub fn of(op: []const u8) i32;
};
```

**Precedence Levels (Lowest to Highest):**
1. Assignment operators (`=`, `+=`, etc.)
2. Logical OR (`||`)
3. Logical AND (`&&`)
4. Equality (`==`, `!=`)
5. Relational (`>`, `>=`, `<`, `<=`)
6. Additive & Pipe (`+`, `-`, `|>`)
7. Multiplicative (`*`, `/`, `%`, `**`)
8. Exponentiation (`^`)
9. Range (`..`)

**Constraints & Rules:**
- The function returns `-1` for unknown or non-operator strings.
- Higher integer values indicate higher binding power.

## Memory Allocators

There are **no dynamic memory allocators** initialized or managed directly within the `src/shared` utilities.
- Operator sets and validations depend entirely on statically allocated constant arrays (`[_][]const u8`).
- String equality is checked directly via `std.mem.eql(u8, ...)`, which operates on stack/pointers and avoids heap allocation.
- When utilizing these shared types across the compiler, the caller component is responsible for providing the string slices (e.g., token views generated by the scanner pointing to the original source file buffer).

## I/O and Logging (`src/io/`)

The `src/io` module provides a robust, centralized subsystem for handling standard output, error streams, and internal compiler logging.

- **`out.zig`**: Provides safe Posix-level wrappers (`writeStdout`, `writeStderr`) that handle short writes and `EINTR` robustly, ensuring output is not dropped during pipeline interruptions. It avoids relying heavily on `std.debug.print` for standard emissions.
- **`color.zig`**: Manages ANSI terminal colors for formatted output. Color usage is toggled automatically via TTY detection or environment variables like `LLTS_COLOR=1` or `NO_COLOR=1`.
- **`log.zig`**: A structured logging facility with severity levels (`trace`, `debug`, `info`, `warn`, `err`). It hooks into the compiler and runtime to format logs with appropriate ANSI colors, and its verbosity can be controlled via the `LLTS_LOG_LEVEL` environment variable or `--log-level` CLI flag.

## Diagnostics and Error Reporting (`src/errors/`)

The `src/errors` subsystem standardizes how errors, warnings, and traces are presented to the user. It is heavily utilized by the VM and compiler to produce rich, TypeScript-style error messages (e.g., inline source snippets with carets pointing to the exact column of the error).

- **`diag.zig`**: Manages the global diagnostic emission state (`wasEmitted()`). This is used by the top-level CLI runner to prevent duplicate, noisy generic errors from bubbling up when a detailed, rich diagnostic has already been printed by the compiler or VM.
- **`report.zig`**: Handles the visual formatting of source context (e.g., `reportSourceError` for inline code snippets) and compilation errors.
- **`stack_trace.zig`**: Unwinds and formats the VM's active call stack during runtime crashes.
- **Integration**: The `compiler` and `vm` modules now route failure paths through this API, leveraging `errdefer` for robust resource cleanup while providing the user with detailed context. Module resolution errors are also routed here for clearer error messaging.

For a deeper dive into runtime error handling and formatting, refer to [errors.md](./errors.md).
